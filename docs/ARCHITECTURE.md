# Architecture

## The one pattern

Almost every feature in this system is the same four steps. Learn it once and the other forty-four
flows read themselves.

1. The browser writes a row describing the work, with `status = 'queued'`.
2. The browser triggers a Flowise flow, passing only the row's id.
3. The flow reads the row, builds a ComfyUI graph in code, submits it, and polls until it finishes.
4. The flow writes the output path back onto the row and sets `status = 'complete'`.

The browser polls the row, or simply reloads the list. Nothing depends on the tab staying open —
close it mid-render and the row still completes.

**Why the row comes first.** It gives the render an identity before it exists. A failure has
somewhere to record itself, a long job survives a refresh, and the history is queryable without a
separate job store.

## Boundaries

| Layer | Does | Never does |
|---|---|---|
| Browser | writes rows, triggers flows, shows results | talk to ComfyUI for work, hold secrets beyond its own env |
| Flowise | reads rows, builds graphs, waits, writes results, calls language models | render anything itself |
| ComfyUI | every GPU operation | know about the database |
| Postgres | every fact | store bytes |

The browser does read from ComfyUI, but only to *display* files, through its `/view` endpoint. That
is why ComfyUI runs with CORS enabled.

## Why Flowise at all

The flows are not conversational agents. Each is a single Custom Function node: a page of
JavaScript with the database URL, its key, and the ComfyUI URL injected as variables. Flowise
supplies the HTTP endpoint, the long-running execution, the secret storage and the edit-and-deploy
loop, so the logic lives in one place instead of in the browser, where it would need the service
key, or in a bespoke server nobody maintains.

Consequence: **the flow sources in `flowise/nodes/` are the real application.** The exported graph
JSONs are wrappers around them.

## Data flow, end to end

```
screenplay or prose
   │  parsed by a language model
   ▼
scenes + beats ──────────────► characters (references generated per character)
   │                                  │
   │ location prose                   │ identity references
   ▼                                  │
360° panorama                         │
   │  invented views + 3D training    │
   ▼                                  │
Gaussian-splat world                  │
   │  measured into a floor plan      │
   ▼                                  │
camera intent per shot  ──► rendered plate ──► cleaned plate
                                          ╲       │
                                           ╲      ▼
                                            ──► generated frame  ──► video clip
                                                                        │
                                                          colour, score, voice
                                                                        ▼
                                                               editorial hand-off
```

## Two ideas worth understanding

**Cameras are stored as intent, not coordinates.** A shot's camera says "stand near the door,
look at the desk, chest height, a third of the way out". It is resolved into a position and a
target against the scene's floor plan at render time. Coordinates would be meaningless to a human
and would break the moment the world was retrained; intent survives both. The same resolver exists
twice, in Python for rendering and in TypeScript for the live UI, and the two are held to
agreement by a cross-language test.

**Worlds are improved, not rebuilt.** A 3D world keeps every training checkpoint it saved and
every camera path it explored. Adding detail at a particular angle means writing one new camera
path, letting the video model invent close views along it, and *continuing* training from the last
checkpoint — minutes, not a day. The coordinate frame is preserved across a continuation, which is
what keeps floor plans and cameras valid.

## Conventions and traps

- **Paths.** Absolute Windows paths in some columns, render-host-relative in others, storage keys
  in a third. A flow must handle all three before loading an image; several do this with a small
  router that branches on the prefix.
- **Schema cache.** After any `ALTER TABLE`, `NOTIFY pgrst, 'reload schema';` or the column is
  invisible to every client.
- **Active project.** Most flows resolve the project from `movies.is_active`. Work on a draft can
  steal activation from whatever else is open; newer flows take the project id explicitly instead.
- **Generated columns.** At least one code column is generated by the database. Writing it errors.
- **Renumbering.** Scene numbers are continuous across acts and are denormalised onto several
  asset tables that have no foreign key back to the scene. Inserting a scene in the middle must
  renumber those together, or a location's panorama silently attaches to the wrong scene.
- **One heavy graph at a time.** Two large submissions will fail on VRAM. Flows free models before
  the big ones.
- **Restart after installing a node pack.** Nothing in the pipeline can reload ComfyUI's node
  registry for you.

## Repository layout as it maps to the running system
